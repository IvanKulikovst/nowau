# Архитектура «Регламент-ТС»

Программа — один офлайн-файл `index.html`: без сервера, без интернета, без внешних библиотек. Данные хранятся в браузере на этом компьютере (localStorage — записи, IndexedDB — вложения и точки восстановления).

Переход к модульной платформе начат **внутри текущего файла**: у каждого модуля есть чёткие границы, владелец данных, версия и самотесты. Разносить модули по отдельным файлам можно позже, не меняя этих правил.

### Правило «новое не ломает работающее»

1. Модуль меняет только **свои** коллекции. Чужие данные читает через публичный API владельца (`TST.fleet`, `TST.catalog`) или узнаёт об изменениях из событий шины.
2. Новые поля записей **добавляются**, существующие не переименовываются и не меняют смысл. Если без этого нельзя — повышается версия структуры данных и пишется миграция.
3. У каждого модуля есть самотесты. Изменение не готово, пока самотесты всех модулей и регрессионные тесты (`tests/`) не проходят.

## Идентификаторы

`<префикс>_<время base36>_<случайная часть>`, допустимые символы `A–Z a–z 0–9 _ -`, длина 4–64 (`TST.platform.ids`).

| Префикс | Запись |
|---|---|
| `v` | единица техники (он же — содержимое QR-кода) |
| `m` | запись ТО или ремонта |
| `h` | показание моточасов |
| `t` | путевой лист |
| `n`, `c` | норматив / правка справочника |
| `r`, `e`, `s` | элемент корзины / запись журнала / точка восстановления |

Идентификатор присваивается один раз при создании и **не меняется никогда**: на нём держатся связи, журнал изменений, корзина и QR-наклейки. Копия записи всегда получает новый идентификатор.

## Модель данных и целостность

Коллекции описываются через `TST.platform.defineCollection(name, { required, refs, unique, check })`:

* `required` — обязательные поля;
* `refs` — связи: `maint.vehicleId → vehicles`, `hours.vehicleId → vehicles`, `hours.maintId → maint`, `hours.tripId → trips`, `trips.vehicleId → vehicles`;
* `unique` — поля, повтор которых — замечание (инвентарный, государственный, заводской номера);
* `check` — правила владельца (допустимые статусы, виды ТО, даты, моточасы).

`TST.platform.checkIntegrity(db)` только находит проблемы; `TST.platform.repair(db)` возвращает исправленную **копию** и перечень исправлений. Проверка выполняется перед восстановлением из копии, перед откатом к точке восстановления и вручную.

## События

Общая шина `TST.on(type, fn)` / `TST.emit(type, detail)`. События платформы — `TST.platform.EVENTS`:

| Событие | Когда |
|---|---|
| `fleet-changed` | данные учёта сохранены |
| `workspace` | переключён раздел приложения |
| `platform:module` | зарегистрирован модуль |
| `platform:integrity` | выполнена проверка целостности |
| `platform:snapshot` | создана точка восстановления |
| `platform:migrated` | структура данных обновлена |
| `platform:tests` | выполнены самотесты |

## Версии и миграции

* Структура данных — `SCHEMA_VERSION` (сейчас **2**). Миграции — список `MIGRATIONS` (раздел 27c): каждая переводит базу на одну версию вперёд и принадлежит модулю.
* Перед миграцией автоматически создаётся точка восстановления со старыми данными. Журнал миграций — `db.migrations`.
* Данные из **более новой** версии программы не понижаются: неизвестные поля и коллекции сохраняются, пользователь получает предупреждение.
* Версия каждого модуля указана при регистрации (`TST.platform.register({ id, version, … })`).

История версий структуры:

| Версия | Что добавлено |
|---|---|
| 1 | исходная структура |
| 2 | корзина `trash`, журнал изменений `history`, журнал миграций, статус «Неисправна»; позже без смены версии добавлены необязательные поля: `maint.checklist` (шаблон работ), `maint.season`, `settings.seasons`, `vehicle.photos`, `vehicle.vdocs`, `vehicle.mainPhotoId` (фото и документы техники) |

## Сохранность данных

| Механизм | Где хранится | Когда |
|---|---|---|
| Резервная копия ZIP (записи + вложения) | файл пользователя | вручную; напоминание через `backupRemindDays` дней |
| Точки восстановления (снимок записей) | IndexedDB `tst-fleet-snapshots` | ежедневно; перед восстановлением из копии, очисткой, миграцией, исправлением, откатом, очисткой корзины; вручную. До 20 автоматических + 20 ручных |
| Корзина | `db.trash` | любое удаление; хранится `trashDays` дней (30) |
| Журнал изменений | `db.history` | изменение важных полей карточки, создание и удаление; до 3000 записей |

Вложения (в том числе фото и сканы документов техники) не удаляются, пока на них ссылается текущая запись, элемент корзины или точка восстановления (`cleanupOrphanFiles`). Фото сжимаются до 1600 px, миниатюры — отдельные файлы (в записи только идентификаторы).

В приложении для Windows (`app/`) записи, вложения и точки восстановления хранятся в файлах (`db.json`, `db.prev.json`, `backups/`, `files/`, `snapshots/`), а не в браузере — см. `app/README.md`.

**Ограничение (режим браузера).** Точки восстановления и корзина лежат в том же браузере, что и данные. От поломки диска или удаления профиля спасает только резервная копия на внешнем носителе.

**Несколько пользователей.** Сейчас программа рассчитана на одного пользователя на одном компьютере. Несколько вкладок синхронизируются трёхсторонним слиянием по записям. Для работы нескольких пользователей понадобятся разграничение доступа и разрешение конфликтов при обмене файлами изменений — это следующий этап.

## Как добавить модуль

1. Выбрать `id` и префикс идентификаторов записей.
2. Описать коллекцию: `TST.platform.defineCollection('parts', { owner: 'warehouse', required: [...], refs: { vehicleId: 'vehicles' } })`.
3. Если коллекция новая — повысить `SCHEMA_VERSION` и добавить миграцию, создающую пустую коллекцию.
4. Зарегистрировать модуль с версией и самотестами: `TST.platform.register({ id, name, version, owns, depends, tests })`. Самотесты работают на временной базе (`withTestDB`) и ничего не сохраняют.
5. Запустить «Самотесты» в программе и `tests/` — все должны пройти.

## Тесты

```
npm i -D playwright && npx playwright install chromium
node tests/platform.spec.js     # платформа, сохранность данных, пункт управления (25 проверок)
node tests/qr.spec.js           # QR-маркировка и регрессия разделов (18 проверок)
node tests/season.spec.js       # шаблоны работ ТО и сезонное обслуживание (20 проверок)
node tests/vfiles.spec.js       # фото и документы техники (28 проверок)
```

Тесты открывают `index.html` без сети: внешние запросы блокируются и подсчитываются.
